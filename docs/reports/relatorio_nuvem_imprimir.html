Planejamento e Análise do Ambiente de Nuvem

Documento técnico-acadêmico de especificação de arquitetura, componentes de infraestrutura, conteinerização, rede, observabilidade e pipeline de deploy para a plataforma gamificada EstudeMy.

1. Resumo Executivo e Contexto do Projeto

O EstudeMy é uma plataforma gamificada de ensino voltada ao aprendizado dinâmico inspirado em dinâmicas de RPG (estilo Duolingo). O sistema integra três frentes: um Aplicativo Móvel em React Native (Expo), uma API RESTful em Node.js (TypeScript) e um Banco de Dados NoSQL MongoDB. O objetivo deste documento é apresentar o planejamento rigoroso da migração da arquitetura para a nuvem, garantindo alta disponibilidade, segurança perimetral, observabilidade em tempo real e entrega contínua.

📱 Mobile App (Frontend)

React Native (Expo SDK 57), Expo Router, navegação por abas e trilhas em zigzag. Compilado para SPA estático para execução em contêiner Nginx e emuladores nativos.

⚙️ API REST (Backend)

Node.js 22 LTS + Express 5 em TypeScript, autenticação JWT com expiração segura, hashing Bcrypt e documentação OpenAPI/Swagger.

🍃 Banco de Dados

MongoDB 7.0 Community Edition, modelagem orientada a documentos BSON para armazenamento ágil de perfis RPG, fases polimórficas e trilhas.

2. Diagnóstico da Situação Atual do Projeto (Cenário AS-IS)

Atualmente, a plataforma opera em regime de desenvolvimento distribuído com dependência de serviços gratuitos em nuvem (PaaS) para testes pontuais:

Componente Implementação Atual Gaps, Gargalos e Riscos Técnicos
API Backend Instância gratuita no Render (estudemydocker.onrender.com). Cold Start severo: O serviço entra em suspensão após 15 minutos ocioso, gerando atraso de ~50s na primeira requisição móvel. Falta IP estático e controle de recursos.
App Mobile Expo Go local via Wi-Fi e build web manual. Depende da máquina local do desenvolvedor ativa para pareamento de testes; sem servidor de borda permanente com cache e CDN.
Banco de Dados Cluster compartilhado MongoDB Atlas (Tier M0 gratuito) / Mongo local. Limite de 512 MB de dados, ausência de backup automatizado pontual e comunicação exposta à internet pública sem VPC privada dedicada.
Rede & Segurança Sem isolamento de rede virtual (VPC/VCN). Endpoints da API acessíveis publicamente sem firewall perimetral, sem VPN para gerência e sem política restritiva de CORS por sub-rede.
Deploy & CI/CD Gatilhos de Git automáticos e builds manuais. Sem testes automatizados antes do deploy, sem versionamento de imagens Docker e sem estratégia de rollback imediato em produção.
Observabilidade Logs de console voláteis e Better Stack básico. Sem métricas em tempo real de infraestrutura (CPU/RAM/disco), sem painéis centralizados (Grafana) e sem alarmes de saturação de hardware.
Conclusão do Diagnóstico AS-IS: A infraestrutura atual atende apenas à fase de prototipagem funcional. Para a disponibilização sustentável e segura em ambiente de nuvem, é mandatória a transição para um modelo estruturado com isolamento de rede (VCN), conteinerização padronizada (Docker), proxy de terminação TLS e automação de deploy via GitHub Actions.

3. Arquitetura Proposta em Nuvem (Cenário TO-BE)

A arquitetura de nuvem proposta adota o padrão Cloud-Agnostic baseado em Contêineres Docker (CaaS sobre IaaS). Esse modelo foi selecionado para viabilizar tanto a execução no Oracle Cloud Infrastructure (OCI Free Tier) — em consonância com as práticas da disciplina do Prof. Benir — quanto na AWS — conforme a ementa central do PI —, sem qualquer acoplamento de código.

5. Definição do Ambiente de Execução

🐧 Sistema Operacional do Host

Ubuntu Server 24.04 LTS (Noble Numbat) 64-bit. Escolhido por ser o padrão de mercado para nuvem corporativa, com ciclo de suporte estendido até 2029, kernel 6.8 moderno, AppArmor nativo e total compatibilidade com Docker Engine e KVM.

📦 Runtimes e Utilitários

Docker Engine 26.x + Docker Compose Plugin v2. Isolamento em contêineres OCI com cgroups v2. Node.js 22 LTS para builds TypeScript e Nginx 1.26 Alpine para entrega web estática ultrarrápida.

6. Estratégia de Utilização de Máquinas Virtuais e Containers

A equipe optou pelo modelo de Contêineres sobre Máquinas Virtuais (CaaS sobre IaaS). Esse arranjo combina o isolamento de hardware e rede da máquina virtual com a flexibilidade, portabilidade e densidade dos contêineres Docker:

Critério Máquina Virtual Pura (VM) Contêineres Docker sobre VM (Adotado) Serviço Serverless Puro
Paridade Dev/Prod Baixa (depende de scripts manuais no SO). Total (o mesmo container roda local e na nuvem). Média (depende de emuladores de nuvem).
Consumo de Recursos Alto (cada serviço requer um SO completo). Otimizado (compartilhamento de kernel e bibliotecas). Variável (sujeito a cold starts).
Tempo de Inicialização Lento (1 a 3 minutos para boot do SO). Instantâneo (1 a 3 segundos por contêiner). Médio (cold starts de 10 a 50s no tier gratuito).
Portabilidade Multi-Cloud Média (formatos de imagem de VM variam). Máxima (padrão OCI executável em OCI, AWS, GCP ou KVM). Baixa (alto acoplamento com o provedor).
7. Definição do Banco de Dados
7.1 Escolha Tecnológica: MongoDB Community Edition 7.0 (NoSQL)

O MongoDB foi escolhido como banco de dados primário do EstudeMy com base em justificativas técnicas de negócio:

  • Fases e Lições Polimórficas: No RPG do EstudeMy, existem fases teóricas (textos, imagens e dicas) e fases de quiz (questões de múltipla escolha com 4 alternativas, código-fonte e justificativas). O modelo NoSQL em documentos BSON acomoda essas variações em uma única coleção (fases) sem necessidade de tabelas associativas complexas de SQL.
  • Progresso Dinâmico do Aluno: O estado de cada usuário (vidas ❤️, moedas 🪙, experiência XP ✨, trilhas concluídas e respostas gravadas) é armazenado como subdocumentos aninhados, permitindo leituras e atualizações atômicas instantâneas.
  • Desempenho e Agilidade Mobile: Consultas de ranking global e busca de trilhas ordenadas são processadas diretamente na memória via índices compostos.
7.2 Topologia de Armazenamento e Rotinas de Backup

💾 Persistência em Bloco

O diretório de dados /data/db do contêiner MongoDB é montado sobre um volume de bloco persistente (Block Volume de 100 GB). Isso assegura que reinicializações ou recriações do contêiner não causem nenhuma perda de dados.

🛡️ Rotinas de Backup & Disaster Recovery

Backup lógico diário automatizado via mongodump com compactação gzip. Os arquivos .gz são sincronizados com o Object Storage Bucket com retenção de 7 dias. RPO estabelecido em 24h e RTO em 15 minutos.

# Script automatizado de backup (Cron Job executado diariamente às 03:00 UTC): docker exec estudemy_mongo mongodump --db estudemy --gzip --archive=/tmp/backup_estudemy_$(date +%F).gz oci os object put -bn backup-estudemy --file /tmp/backup_estudemy_$(date +%F).gz

8. Estratégia de Disponibilização do Frontend e Backend

⚙️ Backend API (Node.js + Express + TypeScript)

  • Compilação multi-stage com Node 22 Alpine gerando artefatos JS em /dist.
  • Execução em contêiner na Subnet Privada na porta 5000.
  • Comunicação exclusiva com o MongoDB na rede Docker interna.
  • Documentação interativa Swagger exposta em /api-docs.
  • Healthcheck ativo na rota raiz GET / para sondas do balanceador.

📱 Frontend Mobile Web (Expo SPA / Nginx)

  • Exportação estática das rotas com npx expo export -p web.
  • Hospedagem em contêiner Nginx Alpine servindo na porta interna 8081.
  • SPA Fallback: try_files $uri $uri.html $uri/ /index.html;.
  • Cache com cabeçalhos immutable para bundles JS, fontes e imagens.
  • Proxy reverso /api/ apontando para a API (sem problemas de CORS).
9. Definição dos Mecanismos de Rede e Acesso

O perímetro de rede é protegido através de regras rígidas de Security Lists / Security Groups, garantindo que apenas as portas essenciais fiquem visíveis para o público externo:

Direção Protocolo Porta Origem / Destino Objetivo e Justificativa
Entrada TCP 443 (HTTPS) 0.0.0.0/0 (Internet) Acesso público seguro à aplicação web e requisições do app móvel.
Entrada TCP 80 (HTTP) 0.0.0.0/0 (Internet) Redirecionamento automático obrigatório para HTTPS (código HTTP 301).
Entrada TCP 22 (SSH) IP do Administrador / VPN Acesso administrativo exclusivo via chave criptográfica (sem login por senha).
Interna TCP 5000 Apenas Rede Docker Comunicação entre Nginx Gateway e a API Backend (bloqueada externamente).
Interna TCP 27017 Apenas Contêiner Backend Comunicação direta entre Mongoose e MongoDB (sem exposição pública).
Saída TCP 443 / 80 0.0.0.0/0 Downloads de dependências, atualizações do SO e chamadas à API Gemini.
10. Estratégia de Monitoramento e Observabilidade

A observabilidade é estruturada sob os Três Pilares da Engenharia de Confiabilidade:

📊 1. Métricas (Prometheus + Grafana)

Coleta contínua de métricas de host (CPU, memória RAM, I/O de disco) via node_exporter e métricas de contêineres via cAdvisor. Painéis no Grafana alertam caso o uso de CPU exceda 80% por 5 min.

📝 2. Logs Estruturados (Better Stack)

Logs gerados pelo Morgan/Winston no backend em formato padronizado JSON (timestamp, rota, método, status HTTP e duração). Ingestão no Better Stack Logs para auditoria e rastreamento de falhas.

🚨 3. Uptime & Alarmes Automáticos

Sonda externa verificando o endpoint de saúde a cada 60s. Em caso de 3 falhas consecutivas ou tempo de resposta superior a 2500ms, notificações automáticas são disparadas para o canal da equipe no Discord/E-mail.

Conformidade com a Disciplina: Esta arquitetura atende integralmente ao requisito de demonstrar métricas de disponibilidade, logs centralizados e monitoramento de saúde do ambiente, conforme estipulado nos itens 10 e 13 das diretrizes de Computação em Nuvem.

11. Planejamento do Processo de Deploy (Pipeline CI/CD)

A automação de deploy utiliza o GitHub Actions integrado diretamente ao repositório Git do projeto, operando em um ciclo automatizado de 5 fases:

Pipeline de Integração e Entrega Contínua (CI/CD)
1. Push Git
Branch main
➔
2. Validação CI
Lint + Jest + TypeCheck
➔
3. Build Docker
Multi-stage Caching
➔
4. Push Registry
GHCR / Docker Hub
➔
5. Deploy CD
SSH + Compose Up

Gestão de Segredos: Todas as credenciais de produção (SSH_PRIVATE_KEY, JWT_SECRET, MONGO_URI) residem exclusivamente no cofre criptografado do GitHub Actions Secrets, sem exposição em arquivos de configuração ou commits.
